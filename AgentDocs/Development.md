# 구현과 검증 지침

## 멀티 에이전트 오케스트레이션

- 개발은 멀티 에이전트 오케스트레이션을 이용해 수행한다.
- 메인 에이전트는 `GPT-6 Astra Ex`를 사용하고, 서브 에이전트의 작업을 배분·조율하며 결과를 통합한다.
- 모든 서브 에이전트는 `GPT-6.1 SOL Ex`를 사용한다.

| 서브 에이전트 | 담당 업무 |
| --- | --- |
| 깃 에이전트 | Git 커밋·push 및 브랜치 등 버전 관리를 담당한다. |
| 기획 확인 에이전트 | 기획서와 개발문서를 읽고 개발해야 할 사항과 개발 완료된 사항을 확인해 메인 에이전트와 개발 에이전트에 전달한다. |
| 개발 에이전트들 | 기획 분야별로 여러 에이전트를 구성해 각 분야의 개발을 수행한다. |
| 배포 검사 에이전트 | GitHub의 `main` 반영 후 Vercel·Render 배포 상태와 배포된 서비스의 AI/PVP 브라우저 동작을 [배포 지침](Deployment.md)에 따라 검증하고, 결과를 메인 에이전트에 전달한다. |

- 메인 에이전트는 기획 확인 결과를 바탕으로 개발 에이전트별 담당 범위와 의존 관계를 정하고, 통합 시 누락과 충돌을 확인한다.
- 개발 과정의 Git 변경은 깃 에이전트가 맡아 중복 실행을 방지하며, [Git·테스트 지침](GitAndTesting.md)의 브랜치·사용자 테스트·병합 제한을 따른다.

## 개발 문서 확인

- 개발 문서를 바탕으로 개발할 때 문서가 불완전하거나 모호한 부분이 있으면 사용자에게 먼저 질문한다.
- 답변을 확인한 후 해당 부분의 개발을 진행한다. 게임 규칙이나 요구사항을 임의로 확정하지 않는다.
- 개발 도중 모호한 사항에 대한 사용자 답변을 받으면 기획 확인 에이전트가 해당 내용을 기획서에 반영한다. 기획서 변경에 따른 개발문서 갱신과 완료 체크 변경은 [문서 관리 지침](Documentation.md)을 따른다.
- 기획·개발 문서는 [문서 관리 지침](Documentation.md)과 [문서 인덱스](../Docs/agents.md)를 따른다.

## 구현

- 변경 전 관련 파일과 현재 Git 상태를 확인하고, 사용자 작업을 보존한다.
- 브랜치 생성·테스트·병합은 [Git·테스트 지침](GitAndTesting.md)을 따른다.
- 앞으로 만드는 모든 게임과 모드는 플레이어가 AI를 상대로 원활하게 1대1 대결할 수 있도록 설계·구현한다.
- 게임 로직과 브라우저 입출력·렌더링은 필요에 맞게 분리한다. 조정할 게임 수치는 한곳에서 찾기 쉽게 관리한다.
- 비밀키·인증 토큰·개인정보를 코드나 브라우저 번들에 넣지 않는다. 환경변수가 필요하면 값 없는 예제를 제공한다.
- 브라우저에 노출되는 `VITE_*` 환경변수에 비밀키를 넣지 않는다.
- 의존성 잠금 파일을 함께 관리한다. 생성물, 의존성 폴더, 로컬 환경변수, Vercel 연결 정보는 커밋하지 않는다.

## 기능 개발 중 검증

- 기능 개발·수정 중에는 개발한 기능, 수정한 코드와 그 변경으로 영향을 받는 부분만 테스트한다. 관련 테스트 파일·케이스를 선별하고 영향받는 기존 기능의 회귀 검증을 포함한다.
- 전체 자동 테스트, 전체 타입 검사와 프로덕션 빌드는 기능마다 실행하지 않는다. 사용자의 실제 `main` 병합·배포 요청 시 [배포 전 dev 전체 검증](Deployment.md#배포-전-dev-전체-검증)으로 모아서 수행한다.
- 입력·화면 크기·재시작·모바일 터치·AI/PVP 브라우저 검증도 개발한 기능과 변경 영향 범위에 한정한다.
- 전체 AI/PVP 브라우저 검증은 [main 병합·배포 완료 후](Deployment.md#배포-후-aipvp-브라우저-검증)에 수행하며, 기능마다 또는 배포 전 `dev`에서 전체 흐름을 반복 검증하지 않는다.
- 수정 중 재검증은 실패한 부분과 변경 영향 범위만 다시 수행한다. 메인 에이전트는 서브 에이전트의 검증 범위·결과를 공유해 동일 코드·환경에 대한 검증을 중복 실행하지 않도록 조율한다.
- 테스트는 오류 위험에 비례해서 추가한다. 단순 문서 수정에 불필요한 테스트를 만들지 않는다.

## 검증과 보고

- 에이전트의 검증 성공은 사용자의 로컬 테스트 완료나 병합 요청을 대신하지 않는다.
- 완료 보고에는 변경 내용, 실제 실행한 검증의 범위·결과, 미확인 사항을 구분한다. 부분 검증을 전체 검증 통과로 보고하지 않는다.
