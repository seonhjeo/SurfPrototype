# Git·브랜치·로컬 테스트 지침

## 개발 작업

- 개발은 `main`이 아닌 `dev`를 기준으로 한다.
- 새로운 개발사항이나 코드 수정은 최신 `dev`에서 새 작업 브랜치를 만든 뒤 수행한다.
- 기존 사용자 작업을 보존하고, 다른 작업의 변경을 임의로 포함하지 않는다.
- 개발에 사용한 브랜치는 병합 후에도 삭제하지 않고 유지한다. 원격에 올린 작업 브랜치도 유지한다.

## 사용자 로컬 테스트와 dev 병합

1. 새 개발사항 구현을 완료하면 관련 정적 검사·빌드·동작 검증을 수행한다.
2. 작업 브랜치의 결과를 로컬 서버로 실행하고, 사용자가 바로 테스트할 수 있도록 브라우저를 팝업한다.
3. 로컬 테스트 URL과 확인할 내용을 안내하고 사용자의 테스트를 기다린다.
4. 사용자가 테스트를 완료하고 `dev`로 병합해 달라고 명시적으로 요청한 때에만 해당 브랜치를 `dev`에 병합한다.

- 사용자 요청 전에는 `dev` 병합을 수행하지 않는다. 에이전트 테스트, CI 성공, Preview 배포 성공, 사용자의 무응답을 병합 요청으로 해석하지 않는다.
- 사용자의 테스트가 끝나기 전에 테스트용 서버를 임의로 종료하거나 테스트 중인 작업 브랜치를 바꾸지 않는다.

## main 보호

- 다른 브랜치에서 `main`으로 임의로 병합하지 않는다. `dev` 병합 요청은 `main` 병합 권한을 포함하지 않는다.
- `main`을 대상으로 하는 Pull Request는 사용자가 수행해 달라고 명시적으로 요청한 경우에만 생성한다.
- `main` 대상 PR 생성 요청만으로 그 PR의 병합까지 허용된 것으로 해석하지 않는다.

## 문서만 수정하는 경우

- 개발 지침, 기획 문서, `AGENTS.md`, `README.md`, `AgentDocs/`, `Docs/` 등 문서만 수정할 때는 `main`에서 직접 작업·커밋하고 `main`에 그대로 push한다.
- 문서만 수정하는 작업에는 새 브랜치나 PR을 만들지 않는다. 다른 브랜치를 `main`에 병합하는 방식으로 처리하지 않는다.
- 코드나 실행 설정 변경이 함께 포함되면 문서 수정 예외를 적용하지 않고 `dev` 기반 작업 브랜치와 사용자 로컬 테스트 절차를 따른다.

## 원격 반영

- 원격 push나 병합은 Vercel 배포를 유발할 수 있다. 해당 작업에 대한 사용자의 승인 범위 안에서 수행한다.
- CI 파일 변경에 필요한 인증 권한 등 배포 관련 사항은 [배포 지침](Deployment.md)을 확인한다.
