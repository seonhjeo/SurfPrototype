# Git·브랜치·로컬 테스트 지침

## 개발 작업

- 개발은 `main`이 아닌 `dev`를 기준으로 한다.
- 새로운 개발사항이나 코드 수정은 최신 `dev`에서 새 작업 브랜치를 만든 뒤 수행한다.
- 기존 사용자 작업을 보존하고, 다른 작업의 변경을 임의로 포함하지 않는다.
- 개발에 사용한 브랜치는 병합 후에도 삭제하지 않고 유지한다. 원격에 올린 작업 브랜치도 유지한다.

## 개발 브랜치 이름

- 새 개발 작업 브랜치의 이름은 `xx.xx.xx-[구현사항]` 형식을 따른다. 예: `0.2.0-private-pvp`.
- 앞의 숫자는 일반적인 소프트웨어 버전 규칙인 `MAJOR.MINOR.PATCH`를 사용하며, 각 숫자는 선행 0 없이 표기한다.
- `MAJOR`는 기존 호환성을 깨는 변경, `MINOR`는 호환성을 유지하는 기능 추가, `PATCH`는 호환성을 유지하는 버그 수정 때 올린다.
- 상위 버전 숫자를 올리면 하위 숫자는 0으로 초기화한다. 구현사항 부분에는 작업 내용을 알아볼 수 있는 짧은 이름을 쓴다.

## 사용자 로컬 테스트와 dev 병합

1. 새 개발사항 구현을 완료하면 개발한 기능과 수정한 코드의 영향 범위만 [개발 지침](Development.md#기능-개발-중-검증)에 따라 테스트한다. 전체 자동 테스트·전체 타입 검사·프로덕션 빌드는 배포 전으로 모은다.
2. 구현과 검증이 완료되면 변경사항을 커밋하고, 구현에 사용한 작업 브랜치를 별도 요청 없이 같은 이름의 원격 브랜치로 자동 push한다.
3. 작업 브랜치의 결과를 로컬 서버로 실행하고, 사용자가 바로 테스트할 수 있도록 브라우저를 팝업한다.
4. 로컬 테스트 URL과 확인할 내용을 안내하고 사용자의 테스트를 기다린다.
5. 사용자가 테스트를 완료하고 `dev`로 병합해 달라고 명시적으로 요청한 때에만 해당 브랜치를 `dev`에 병합한다.
6. 승인된 개발사항을 `dev`에 병합·push한 뒤에는 [배포 지침](Deployment.md#main-대상-자동-pr)에 따라 `dev` → `main` PR을 별도 요청 없이 자동 생성·갱신한다.

- 사용자 요청 전에는 `dev` 병합을 수행하지 않는다. 에이전트 테스트, CI 성공, Preview 배포 성공, 사용자의 무응답을 병합 요청으로 해석하지 않는다.
- 사용자의 테스트가 끝나기 전에 테스트용 서버를 임의로 종료하거나 테스트 중인 작업 브랜치를 바꾸지 않는다.

## main 보호

- `main`에 대한 직접 push와 직접 merge를 금한다. 지침·문서만 수정하는 경우에도 예외를 두지 않는다.
- `dev` 병합 요청은 `main`에 대한 push 또는 병합 권한을 포함하지 않는다.
- `main` 대상 PR의 생성·갱신은 [배포 지침](Deployment.md#main-대상-자동-pr)의 자동 수행 조건을 따르며, 해당 조건을 충족하면 별도 요청 없이 수행한다. 사용자의 명시적인 PR 요청도 수행할 수 있다.
- PR 생성·갱신 권한은 직접 push·merge 금지의 예외가 아니며, 그 PR의 병합까지 허용된 것으로 해석하지 않는다. PR 병합은 사용자가 명시적으로 요청한 경우에만 수행한다.
- 사용자가 실제 `main` 병합·배포를 요청하면 [배포 전 dev 전체 검증](Deployment.md#배포-전-dev-전체-검증)을 수행한다. 실패한 부분을 수정·재개발하고 최종 `dev`의 전체 검증을 통과하기 전에는 `main`에 반영하거나 배포하지 않는다.

## 문서만 수정하는 경우

- 개발 지침, 기획 문서, `AGENTS.md`, `README.md`, `AgentDocs/`, `Docs/` 등 지침·문서만 수정할 때는 최신 `dev`에서 직접 작업·커밋하고 `dev`에 그대로 push한다.
- 지침·문서만 수정하는 작업에는 새 브랜치나 자동 PR을 만들지 않는다. 문서만의 PR은 사용자가 별도로 요청했을 때 생성하며, 문서 반영을 위해 `main`에 직접 push하거나 병합하지 않는다.
- 코드나 실행 설정 변경이 함께 포함되면 문서 수정 예외를 적용하지 않고 `dev` 기반 작업 브랜치와 사용자 로컬 테스트 절차를 따른다.

## 원격 반영

- 원격 push나 병합은 Vercel 배포를 유발할 수 있다. 해당 작업에 대한 사용자의 승인 범위 안에서 수행한다.
- CI 파일 변경에 필요한 인증 권한 등 배포 관련 사항은 [배포 지침](Deployment.md)을 확인한다.
